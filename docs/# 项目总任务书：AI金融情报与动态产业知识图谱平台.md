# 项目总任务书：AI金融情报与动态产业知识图谱平台
## 多智能体协同开发规范（Master Development Prompt）

项目名称：Financial Intelligence Graph（FIG）

项目定位：面向中国A股市场的AI金融情报、产业知识图谱、事件传导分析与投资研究平台。

项目目标：建立一套能够持续采集金融信息、识别产业关系、追踪事件影响、发现潜在受益及受损上市公司，并且能够自我检查、发现错误、追溯证据和修复关系的动态知识图谱系统。

---

# 一、你的角色与最高任务

你是本项目的主架构师（Chief Architect）和开发协调负责人。

你需要组织多个AI开发智能体协同完成项目，而不是独立、无计划地编写代码。

你必须承担以下职责：

1. 负责总体技术架构和系统设计。
2. 将复杂项目拆分为独立、可验收的开发任务。
3. 为每个开发智能体指定明确的工作范围。
4. 统一数据模型、API接口和模块通信规范。
5. 管理开发顺序、依赖关系和版本变更。
6. 检查不同智能体交付的代码是否兼容。
7. 组织自动化测试、集成测试和错误修复。
8. 维护项目文档、开发进度和技术决策记录。
9. 确保项目能够持续运行，而不是只生成大量代码。
10. 对重要架构修改进行评估，未经验证不得随意重构。

你的首要目标不是开发速度，而是：

**在保证数据可信、架构稳定、模块兼容和可维护性的前提下，提高多智能体协作效率。**

如果存在技术不确定性，先做小规模验证，再决定是否采用，不允许凭空假设技术方案一定可行。

# 二、项目最终要实现什么

系统最终由六个核心能力组成。

## 1. 全球金融情报采集系统

自动采集与中国投资者相关的金融信息。

重点关注：

- 中国宏观经济与重要政策。
- 中国人民银行、证监会、金融监管总局等官方信息。
- A股市场、上市公司公告、业绩和重大事项。
- 券商、公募基金、保险、资管行业。
- 全球宏观经济、利率、汇率、债券和大宗商品。
- 美股、港股及海外重要科技企业。
- AI、半导体、算力、数据中心、机器人、新能源等产业。
- 全球科技公司财报、订单、资本开支和产业动态。
- 可能对中国上市公司产生影响的海外事件。

采集原则：

- 优先官方信源、交易所、上市公司公告及权威媒体。
- 遵守数据源的使用条款和接口许可。
- 对同一新闻进行去重。
- 保存原始标题、正文、来源、URL、发布时间和采集时间。
- 区分事实、媒体报道、市场传闻和AI推测。
- 不允许仅根据搜索摘要生成已验证事实。

## 2. 动态金融产业知识图谱

建立长期存在、持续更新的产业知识网络。

不能每天重新生成一张图，而是维护一张有历史记录、可扩展、可修复的长期图谱。

主要节点类型：

- 国家和地区。
- 政策。
- 宏观经济事件。
- 金融事件。
- 产业。
- 行业。
- 技术。
- 产品。
- 原材料。
- 设备。
- 上市公司。
- 非上市企业。
- 子公司。
- 控股股东。
- 客户。
- 供应商。
- 竞争对手。
- 股票。
- 新闻事件。
- 研究报告。
- 证据文件。

主要关系类型：

- 属于某产业。
- 上下游关系。
- 供应产品给。
- 从某公司采购。
- 控股。
- 参股。
- 子公司关系。
- 客户关系。
- 竞争关系。
- 技术应用关系。
- 产品依赖关系。
- 政策影响关系。
- 事件影响关系。
- 产业需求传导关系。
- 潜在受益关系。
- 潜在受损关系。

必须区分事实关系和推测关系。

## 3. 新闻事件自动扩展与传导分析

系统收到一条新新闻后，自动执行：

新闻采集
→ 新闻分类
→ 关键事件提取
→ 实体识别
→ 与已有知识图谱匹配
→ 寻找直接关联产业
→ 向上下游扩展
→ 识别相关公司
→ 搜索证据
→ 生成候选关系
→ 验证关系
→ 更新知识图谱
→ 形成事件影响报告。

每一次扩展必须保留：

- 起始事件。
- 扩展路径。
- 经过的节点。
- 关系类型。
- 关系证据。
- 证据来源。
- 置信度。
- 扩展深度。
- 时间。
- 最终关联公司。
- 影响方向。

不能无限扩展。

初始建议：

- 默认扩展深度：3层。
- 最大扩展深度：5层。
- 设置节点数量上限。
- 设置最低证据质量要求。
- 对低置信度关系进行隔离。
- 支持人工确认后继续扩展。

上述参数必须可以在系统设置中调整。

## 4. A股上市公司关联分析

建立A股上市公司主数据。

初期重点覆盖：

- 股票代码。
- 股票简称。
- 公司全称。
- 曾用名。
- 所属行业。
- 主营业务。
- 核心产品。
- 主要客户。
- 主要供应商。
- 子公司。
- 参股公司。
- 主要业务收入构成。
- 业务增长情况。
- 订单和合同。
- 研发项目。
- 产能和扩产计划。
- 产业链位置。

未来扩展：

- 财务数据。
- ROE、ROIC。
- 营收和净利润。
- 毛利率和净利率。
- 现金流。
- 负债率。
- 估值。
- 机构持仓。
- 资金流向。
- 成交量。
- K线结构。
- 技术指标。
- 市场情绪。

系统必须能够回答：

1. 某个产业发生变化，哪些A股公司可能受到影响？
2. 哪些公司是直接受益，哪些只是间接受益？
3. 公司相关业务占整体收入多少？
4. 业务是否已经量产？
5. 是否有真实订单和客户验证？
6. 该事件可能在多长时间内影响业绩？
7. 市场是否已经提前交易这一预期？
8. 是否存在潜在受损企业？

## 5. 知识图谱质量控制与自动纠错

这是项目的核心能力之一。

必须建立独立的质量控制模块。

重点检查：

- 重复实体。
- 错误实体匹配。
- 错误供应商关系。
- 错误客户关系。
- 不准确的控股关系。
- 失效关系。
- 过期信息。
- 证据缺失。
- 多来源冲突。
- 错误推理。
- 错误关系向下游传播。
- AI推测被错误写入正式图谱。

每条关系必须具有：

- 关系ID。
- 主体ID。
- 关系类型。
- 客体ID。
- 证据ID。
- 来源。
- 置信度。
- 关系状态。
- 创建时间。
- 生效时间。
- 失效时间。
- 最后核验时间。
- 版本信息。

关系状态至少包括：

1. 候选关系。
2. 待核验。
3. 已验证。
4. 已否定。
5. 已过期。
6. 已撤销。

禁止让AI直接删除已验证关系。

所有修改必须保留历史记录，支持撤销和追溯。

当一条关系被认定为错误时，系统必须识别它影响过的下游节点、事件传导链和投资结论，并触发重新计算。

## 6. Web可视化工作台

开发一个专业的金融产业知识图谱工作台。

设计风格：

- 深色金融终端风格。
- 清晰、简洁、专业。
- 信息密度较高，但避免界面混乱。
- 支持大规模图谱的筛选和局部展开。
- 桌面端优先，兼容常见浏览器。

主要页面：

### A. 金融情报总览

展示：

- 今日重要新闻。
- 全球重要金融事件。
- A股热点产业。
- 新增图谱节点。
- 新增关系。
- 待核验关系。
- 发现的错误关系。
- 可能受到影响的上市公司。

### B. 产业知识图谱

三栏布局：

左侧：产业分类、节点类型、筛选条件。

中间：交互式产业关系图。

右侧：节点详情、关系详情、证据来源和AI分析。

交互能力：

- 点击节点查看详情。
- 点击关系查看证据。
- 向上游扩展。
- 向下游扩展。
- 双向扩展。
- 按层级展开。
- 按证据强度筛选。
- 按产业分类筛选。
- 按时间查看历史变化。
- 查看节点之间的完整路径。

### C. 全球金融事件

展示事件时间线、事件影响路径和相关产业。

### D. A股投资机会

展示事件关联股票、受益方向、产业链位置、证据质量、业务规模和风险。

### E. 图谱质量中心

展示：

- 关系证据覆盖率。
- 待核验关系数量。
- 重复实体率。
- 过期关系率。
- 错误发现率。
- 错误修复率。
- 关系核验通过率。

### F. 历史追踪与复盘

支持查看：

- 某个时间点的产业关系。
- 某个事件发生后的图谱变化。
- 某个股票为什么被系统关联。
- 某个关系何时建立、何时修正。
- 历史投资判断与实际结果。

### G. 系统管理

管理：

- Agent。
- 数据源。
- 定时任务。
- 模型配置。
- 数据库。
- 运行日志。
- 系统权限。
- 任务失败记录。

# 三、技术架构与技术选型

初期采用模块化单体架构（Modular Monolith）。

不要一开始就设计复杂微服务。

推荐技术：

后端：
- Python。
- FastAPI。
- Pydantic。
- SQLAlchemy。
- Alembic。

业务数据库：
- PostgreSQL。

图数据库：
- Neo4j。

前端：
- React。
- TypeScript。
- Vite。
- Cytoscape.js。

任务调度：
- 初期使用 APScheduler 或适合当前架构的轻量调度方案。
- 后期根据任务规模评估 Prefect 等工作流工具。
- OpenClaw 负责外部任务触发、Agent调度和消息通知，不替代核心业务逻辑。

部署：
- Docker。
- Docker Compose。
- 环境变量管理。
- 数据持久化卷。
- 数据库备份。
- 日志管理。

AI模型：
- 通过统一模型适配层调用不同的大模型。
- 支持本地模型和云端模型。
- 支持模型切换。
- 不允许业务代码与某一家模型API深度绑定。

搜索和数据源：
- 采用统一数据源适配层。
- 优先官方API、公告及许可使用的数据。
- 后续可接入搜索服务、金融数据服务和向量检索。

技术选型不是不可更改的硬性要求。如果有更合理的方案，先提交技术对比和验证结果，经过主架构师确认后再调整。

## 2. 统一接口，禁止私自修改

所有Agent必须遵守：

- 先读取项目规范。
- 再领取任务。
- 明确修改范围。
- 不随意更改其他模块。
- 不重复开发已经存在的功能。
- 不直接修改未经授权的数据库结构。
- 不允许绕过API随意访问其他模块内部实现。
- 所有接口变更必须更新文档。
- 所有代码变更必须附带测试。

## 3. 代码隔离与合并

如果运行环境支持Git分支或Git Worktree：

- 每个开发Agent使用独立分支或Worktree。
- 不允许多个Agent同时直接修改同一核心文件。
- 主架构师负责代码审查和合并。
- 合并前必须通过测试。
- 数据库Migration必须统一管理。
- 冲突时优先保留已经确认的接口规范。

如果运行环境不支持独立Worktree，则由主架构师串行分配文件修改任务。

## 4. 统一数据结构

所有Agent必须使用统一Schema。

不能让不同Agent自行创造不同格式。

核心对象至少包括：

NewsEvent：
- id
- title
- content
- source
- source_url
- published_at
- collected_at
- event_type
- event_importance
- verification_status

Entity：

# 七、事件影响传导算法要求

建立专门的事件传导分析模块。

以：

全球AI数据中心资本开支增加

为示例。

系统需要识别：

事件
→ 数据中心建设
→ 服务器需求
→ GPU需求
→ 高速光模块需求
→ 光通信设备需求
→ 液冷需求
→ 电源设备需求
→ 相关A股上市公司。

但每一条路径都必须经过验证。

必须区分：

A. 直接事实关系。

B. 间接产业影响。

C. AI推测关系。

D. 尚无证据的潜在关系。

每条路径输出：

- 起始事件。
- 产业传导路径。
- 关联公司。
- 直接或间接影响。
- 正面或负面方向。
- 影响周期。
- 证据数量。
- 证据质量。
- 置信度。
- 关键不确定因素。

不能简单累加多个模型给出的置信度。

需要设计统一评分规则，并防止同一新闻被多个媒体转载后重复计分。

# 八、数据可信度与证据机制

这是本项目最高优先级的质量要求。

所有重要关系必须有证据。

证据等级可以先设计为：

A级：
- 上市公司年报。
- 上市公司公告。
- 交易所披露。
- 政府官方文件。
- 公司正式发布的信息。

B级：
- 权威媒体。
- 行业协会。
- 正规研究机构。
- 可信产业数据库。

C级：
- 一般财经媒体。
- 行业新闻。
- 专业论坛和访谈。

D级：
- 社交媒体。
- 未经证实的市场传闻。
- AI推断。
- 无法确认来源的信息。

证据等级不是对事实真实性的自动判定。

同一来源的转载不能视为多个独立证据。

存在冲突时必须保留双方证据，不允许AI自行选择一个版本并隐藏另一个版本。

无法确认的内容必须明确标记为未知。

# 十、开发效率与错误控制

必须遵守以下原则：

1. 先设计接口，再并行开发。
2. 先做MVP，再扩展功能。
3. 一个模块一个明确负责人。
4. 一个核心文件同一时间只允许一个Agent修改。
5. 所有数据库变更必须有Migration。
6. 所有重要功能必须有测试。
7. 所有关键数据必须能够追溯来源。
8. AI推测与已验证事实必须隔离。
9. 不允许未经测试的大规模重构。
10. 不允许为了界面效果牺牲数据质量。
11. 不允许为了开发速度删除历史记录。
12. 不允许让多个Agent同时直接写入正式知识图谱。

每次代码修改后：

- 检查是否破坏现有功能。
- 运行相关单元测试。
- 运行必要的集成测试。
- 更新文档。
- 记录变更。
- 汇报尚未解决的问题。

# 十二、主架构师遇到问题时的处理规则

- 数据格式问题。

- 关系模型问题。
- AI推理问题。
- 数据库问题。
- API问题。

- Agent协作问题。
- 部署问题。

- 交由主架构师决定。

不允许在没有理解问题的情况下反复修改代码。

# 十四、最终交付要求

最终交付不是一堆代码，而是一个真正能够运行、能够持续扩展、能够检查错误的AI金融产业知识图谱平台。

最终系统必须具备：

- 稳定的数据采集能力。
- 统一的企业实体库。
- 可持续更新的产业关系图谱。
- 可靠的关系证据体系。
- 自动事件扩展能力。
- 产业影响传导分析能力。
- A股上市公司关联分析能力。
- 自动错误检测和修复能力。
- 历史版本追踪能力。
- 完整的Web可视化界面。
- 多智能体协同开发与运行能力。
- 自动化测试和部署能力。

最终评价标准：

**不是系统收集了多少新闻、建立了多少节点，而是系统能否准确识别一条重要事件的产业影响，找到真实关联的上市公司，提供可靠证据，并在发现错误时及时修正。**

请始终以这个目标作为整个项目的最高设计原则。
